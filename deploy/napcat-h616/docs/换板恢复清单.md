# 自用源码备份与换板恢复

本项目按当前已运行的个人部署保存，不要求改造成通用产品，也不要求先拆除B站依赖。GitHub用于记录源码和版本；真实配置及运行数据另行私密备份。

## 源码需要保留什么

- 本项目的board、tools、tests、docs、根目录三个cmd和README。
- board/bootstrap中的独立用户环境准备、下载、QQ/NapCat安装、临时挂载、OneBot配置和转发启用脚本。这些是当前实施记录，不能无检查地在任意新系统上直接运行。
- 已有B站项目的Linux部署代码：QQ的时间保护使用 `/overlay/b-up/app/timeguard.py`，配图复用同目录的dynamic_images.py及已有飞书配图应用配置。
- 软件来源、版本、校验值及文件快照清单。源码备份不包含QQ安装包、完整rootfs或系统镜像。

## 必须私密保管，不能上传GitHub

| 内容 | 开发板当前路径/用途 |
| --- | --- |
| QQ转发配置 | `/overlay/napcat-lab/forward-config.json`，含群名单、排除关键词、Webhook、签名、OneBot密钥和首次基准 |
| QQ密码配置 | `/overlay/napcat-lab/private/qq-login.json`，权限保护的明文敏感凭据 |
| 飞书配图与B站配置 | `/overlay/b-up/data/config.json`，含应用凭据及可能的Cookie等 |
| 待发送队列与游标 | `/overlay/napcat-lab/forward-outbox.sqlite3`，迁移前做一致性备份 |
| 尚未发送的图片 | `/overlay/napcat-lab/forward-cache/pending`，与队列一起保存 |
| 登录与WebUI配置 | rootfs内QQ数据、napcat/config；包含Token或会话，按需要私密备份 |
| B站队列/状态 | `/overlay/b-up/data`内的队列与游标，避免恢复后重发或漏抓 |

消息正文、Cookie、密码、密钥、二维码日志、rootfs及数据库备份不要放进公开仓库。现有 `91w/Monitor-Bilibili-up_post` 是公开仓库；自用备份的目的不改变其公开可见性。公开源码文档也应替换个人群号、账号和电脑路径；真实取值保存在私密配置里。

## 换板顺序

1. 确认新板CPU架构、系统、内核、存储挂载和cgroup版本。若使用完整64位Linux，未必需要当前ARM32宿主上的chroot方案；cgroup v2需适配当前启动保护脚本。
2. 准备系统、网络、可信时间和Python环境，先恢复已有B站部署及共享依赖。不能把旧板的“时间已可信”状态直接当成新板校时成功。
3. 按当前版本准备QQ/NapCat和用户环境。安装依赖以QQ包的Depends为准，另准备Xvfb、xauth和dbus等；Tina普通用户联网还涉及inet组3003，其他系统应按实际情况处理。
4. 将board/maintenance脚本放到 `/overlay/napcat-lab`，将board/relay脚本放到其relay子目录。按bootstrap记录核对用户、目录权限、只读/临时挂载及回环监听。
5. 旧板停止QQ与转发写入后迁移配置、队列、游标和待发送图片，或使用SQLite备份接口生成一致性副本。不要只拷贝仍在写入的.db而忽略WAL。
6. 恢复私密配置；新设备可能需要首次手机授权。已有密码回退在旧板已实测成功，不代表新板一定免设备验证。WebUI与OneBot密钥可重建，但两端必须匹配。
7. 核对QQ在线、两个群成员身份和补查、关键词排除、飞书文字/配图、密码回退及时间保护。迁移时不要同时让新旧板转发同一批消息。
8. 验证后登记新系统的开机启动，再停用旧板。手机提醒、维护策略和资源占用都应复查。

源码记录不等于可直接启动的整卡镜像；若还需系统级快速恢复，可另外私密保存可验证的系统镜像，但不把含登录态的整卡镜像上传GitHub。

当前已验证75项组件测试，密码回退在设备验证设置调整后约52秒恢复在线，双群补查及飞书验证通过。长期无人值守和新板适配仍需要在对应设备上验证。
