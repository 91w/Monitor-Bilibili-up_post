# NapCat 长期运行存储维护

2026-11-11 已部署到开发板。维护服务独立运行，已登记开机启动；不需要让电脑一直连接。后续已部署 QQ 管理员消息转发服务与独立飞书群配置，详见 [可靠转发使用说明](可靠转发使用说明.md)。

## 自动维护规则

| 对象 | 规则 |
| --- | --- |
| 受控启动入口捕获的控制台日志 | 每份最多 2 MiB，保留 3 份备份，即每个启动标签最多约 8 MiB |
| NapCat 文件日志 | 已关闭；控制台级别调至 warn，下次 QQ 启动生效 |
| 测试日志、诊断日志、崩溃转储 | 通常保留 7 天；各类另设容量预算 |
| 浏览器明确命名的缓存目录 | 通常保留 30 天，预算 256 MiB |
| 转发完成的媒体临时目录 | 保留 1 天，预算 512 MiB；正式转发需遵守此目录约定 |
| 已下载的三个安装包 | 保留 14 天后可删除，已安装程序保留 |
| apt 下载缓存 | 通常保留 7 天，预算 256 MiB |

容量超过预算时，允许提前删除超过 24 小时、未被进程打开的匹配文件；预算不代表磁盘配额，正在使用及新生成的文件可能暂时超过预算。

北京时间每天 03:00 后执行当天清理；若届时离线，下次维护时补做。每 60 秒检查磁盘余量，每约 10 分钟统计 QQ 用户目录大小。空间紧张时提前清理。只有时间校准可信时才按日期删除，避免时钟错误误删。

## 数据保护与容量上限

通用缓存清理采用目录和文件类型白名单，不遍历删除任意文件，不处理QQ登录信息、数据库、原生图片/语音、配置凭据或待发送媒体；不跟随符号链接，不删除检测到仍被进程打开的文件。另有独立的 [原生消息库定时清理](原生消息库定时清理.md)，只在QQ停止写入后轮换明确的消息文件。

| 条件 | 动作 |
| --- | --- |
| 可用空间低于 5 GiB，或 QQ 用户数据达到 3 GiB | 进入预警状态，尝试清理允许清理的缓存 |
| 可用空间低于 3 GiB，或 QQ 用户数据达到 4 GiB | 暂停受控 QQ 进程并禁止从受控入口再次启动，保留数据库和登录信息 |

总体容量保护与消息库轮换独立。消息文件达到3 GiB时可以由独立维护服务轮换；其他原生资料、图片和表情仍可能增长，达到整个用户目录4 GiB阈值后仍会暂停QQ，需要人工处理。整个目录3 GiB预警继续保留。不能承诺QQ永远无需维护。保护范围是提供的受控QQ入口。

QQ 项目的独立飞书 Webhook 已配置，容量告警具备发送条件；当前容量正常，没有触发容量告警。容量提醒发送到 QQ 通知群。

## 查看与恢复

以下命令在开发板终端执行：

```sh
cat /overlay/napcat-lab/storage-health.json
```

`level=ok` 表示容量正常，`hold_active=true` 表示启动被保护机制暂停。维护脚本位于 `/overlay/napcat-lab/storage_maintenance.py`，通过 init 自动拉起。

不要为了释放空间直接删除 `.config/QQ` 或 `nt_db`。先停止 QQ，再确认需要归档的内容。人工处理后，只有剩余空间至少 5 GiB、QQ 用户数据小于 3 GiB，才能执行：

```sh
/overlay/b-up-runtime/python/bin/python3 /overlay/napcat-lab/storage_maintenance.py --resume
```

该命令只解除保护，不自动启动 QQ。
