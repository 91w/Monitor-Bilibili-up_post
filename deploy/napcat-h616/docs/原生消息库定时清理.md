# 原生消息库定时清理

2026-11-11 已完成可回滚实机验证并启用后台维护。无需自定义NapCat插件，也不直接修改加密数据库中的记录。

## 当前规则

| 项目 | 设置 |
| --- | --- |
| 检查时间 | 每天北京时间03:00后；当时未运行则之后补做 |
| 清理条件 | 白名单消息文件合计达到3 GiB（3072 MiB，2026-11-11按用户要求提高） |
| 频率限制 | 两次维护至少间隔7天，并且上一次备份保留期已结束 |
| 必须满足 | 时间校准可信、QQ在线、双群补查最近5分钟内完成、转发队列无积压、可用空间至少5 GiB |
| 旧文件备份 | 私密备份，只有重建验证通过满24小时后才删除；未验证的备份不删除 |

**每天检查不等于每天清空，更不等于每天重启QQ。** 上次重建验证时消息文件约2.43 MiB，远低于3 GiB，因此低于阈值时不会重启QQ。

## 实际如何清理

1. 检查转发队列与补查状态，暂停接收/发送，等待受控QQ进程退出、数据库文件关闭。
2. 将消息文件逐个原子移动到私密备份目录，保存文件名、大小、校验值及操作阶段。
3. 恢复QQ运行，让QQ自行建立新的本地消息库。
4. 确认是原账号、QQ在线、双群补查完成、消息库已重建。通过后开始计算24小时备份保留期。
5. 保留期结束且时间可信时，验证备份完整性，再删除旧消息文件，回收它们的磁盘空间。

仅处理 `nt_msg.db`、`group_msg_fts.db`、`buddy_msg_fts.db`、`discuss_msg_fts.db`、`data_line_msg_fts.db`、`msg_fts.db` 及对应WAL、SHM和修复材料文件。登录信息、联系人资料、群资料、设置、表情资源、QQ原生媒体和我们自己的转发队列不在轮换名单里。

这会**重建整个本地消息库**，不是逐条删除7天前的记录。之后QQ可能从服务端重新同步部分近期历史；未承诺保留固定天数的原生历史。我们自己的持久化转发队列独立保存，清理前必须无积压。

## 必须知道的限制

- 实际轮换需要短暂退出QQ；期间不能实时接收。恢复后会尝试补查，但QQ服务端不可用的历史无法保证补回。
- QQ可能要求手机授权。初次清理测试需要扫码；后续配置密码并调整设备验证设置后，受控重启复测已自动密码登录成功。自动任务仍在维护后超过约2分钟未就绪时，向独立QQ通知飞书群发送一次维护提示。
- 清理程序不能绕过QQ账号验证，密码回退虽已实测成功，未来仍可能需人工确认。3 GiB阈值与7天间隔用于减少不必要的退出。
- QQ整个用户目录的3 GiB预警、4 GiB暂停保护继续保留。这里的整个目录还包含资料、表情、媒体等，因此总量保护仍可能先触发，尤其是媒体占用较大或增长很快时。
- 若时间不可信、有待发送消息、补查未完成或空间不足，本轮不清理。
- 若断电中断轮换，会保留操作记录和原文件，可能需要人工恢复。不要手动删除备份、WAL或SHM文件。
- 其他原生资料、表情及媒体可能继续占用空间，仍由总体容量保护兜底；本功能只控制列出的消息文件。

## 查看状态与恢复

在开发板终端执行：

```sh
/overlay/b-up-runtime/python/bin/python3 /overlay/napcat-lab/native_history_service.py status
```

`stage=verified` 表示本次重建已验证。`awaiting_verification` 或 `needs_phone_login` 表示尚未通过恢复检查，应先打开QQ管理页检查登录及队列。

需要恢复原消息库时，在备份未删除前执行：

```sh
/overlay/b-up-runtime/python/bin/python3 /overlay/napcat-lab/native_history_service.py rollback
```

恢复也需要停止QQ写入，并可能需要再次手机授权。程序会校验备份，保留重建后的消息文件供排查。应优先让助手核对状态，避免丢失清理后新接收的本地历史。

源码位于 `board/maintenance/native_history.py`、`board/maintenance/native_history_service.py`，私密策略与状态在开发板 `/overlay/napcat-lab/native-history-policy.json`、`native-history-state.json`，备份位于同目录的 `native-history-backups`。交付目录不包含真实聊天数据库、登录凭据或备份内容。
