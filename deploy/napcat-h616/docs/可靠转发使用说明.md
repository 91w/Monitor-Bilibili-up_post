# QQ 管理员消息 → 飞书

## 当前配置

仅处理 QQ 群 `200000001`、`200000002` 的管理员发言。群主目前不包含在内；其他群、普通成员、私聊、匿名消息和自身消息不进入转发存储。管理员消息的文字中只要包含“王座专属”，整条消息排除：不入队、不转发、不下载配图。关键词可跨相邻文字片段匹配，不识别图片中的文字。消息推送到单独的飞书群。

程序已部署并登记开机启动，首次基准从启用时刻开始，之前的历史聊天不补发。两个群的成员身份与历史补查均已实测通过；一条普通成员新消息未进入队列。**QQ 必须保持登录，才具备实际接收条件。**

## 平时怎么使用

保持开发板独立供电和网络连接即可。管理入口使用 [打开正在运行的QQ管理页.cmd](../打开正在运行的QQ管理页.cmd)，临时通过USB恢复电脑固定16099端口，关闭工具会保留网页入口。USB拔插或电脑重启后重新运行工具恢复。关闭网页不会停止转发；不要再用原来的15分钟测试入口启动第二个实例。详见 [WebUI访问与定时清理](WebUI访问与定时清理.md)。

QQ 会在启动时尝试快速登录已有账号；登录态失效或手机要求确认时，仍需人工扫码授权。守护进程不能代替手机授权。

## 消息处理与保留

1. NapCat 把事件推送到开发板的回环地址，使用 HMAC 验证来源；接口不对局域网开放。
2. 先做群号和管理员筛选，匹配后才写入 SQLite 队列，并提交到磁盘；不匹配的内容不入库、不下载媒体。
3. 匹配消息中的图片保存到转发专用目录，再生成持久化发送计划。保留原文，长文字拆分发送；图片逐张发送。
4. 飞书接口明确返回成功后记录进度；失败按约 5 秒起步、最长 30 分钟间隔持续重试，不因次数用完而丢弃。
5. 成功消息的专用图片副本约 1 天后清理，消息正文和发送计划保留 7 天；之后只保留消息哈希等去重信息，约 90 天后清理。失败消息及所需图片持续保留。

目前直接转发文字、链接和图片；QQ 表情及引用显示文字标识。语音、视频、文件、合并转发等类型显示附件类型提示，尚未实现原附件转存或展开。图片下载/上传失败会保留队列继续重试，不静默变成“已成功”。

图片上传复用开发板上已有飞书配图应用的上传凭据；QQ 项目的目标群 Webhook 和签名独立存储。交付目录不保存这些凭据。

## 可靠性的实际边界

- 每分钟仅对两个目标群补查历史，非匹配历史仅在内存筛选。每轮最多 20 页、每页 50 条；未完成会保留分页进度继续，接口失败不推进完成游标。
- 补查依赖QQ还能提供的历史。断电、长时间离线、历史被清理或接口异常时，不能承诺绝对不漏消息。原生消息库维护只在队列无积压且补查完成时轮换，退出期间仍存在接收空窗。
- 补查若缺少发送者身份，会查询其当前群角色；无法还原角色变动前的历史身份。
- 本地重复事件会去重，分段发送会保存进度。若飞书已收到，但响应丢失或进度提交前断电，重试可能重复；Webhook 没有在此实现“恰好一次”发送。每条文字包含原 QQ 消息编号，方便辨认。
- 发送前必须通过时间校准检查。时间不可信时暂停发送，队列保留。
- QQ 子进程保持 512 MiB 内存上限，主机可用内存过低会停止并由守护进程稍后重试；监测数据只保留最近 600 个采样，日志自动轮换。进程崩溃会自动拉起，登录态失效仍需人工处理。

## 查看、暂停与恢复

以下命令在开发板终端执行：

```sh
/overlay/b-up-runtime/python/bin/python3 /overlay/napcat-lab/relay/relay_ctl.py status
/overlay/b-up-runtime/python/bin/python3 /overlay/napcat-lab/relay/relay_ctl.py stop
/overlay/b-up-runtime/python/bin/python3 /overlay/napcat-lab/relay/relay_ctl.py start
```

`status` 只输出在线状态、队列数量和补查状态，不输出消息正文或凭据。`stop` 保留待发送消息；`start` 不清空旧队列。如果容量保护已暂停 QQ，先按 [存储维护策略](存储维护策略.md) 处理。

私密配置位于开发板 `/overlay/napcat-lab/forward-config.json`，队列位于 `/overlay/napcat-lab/forward-outbox.sqlite3`，匹配图片位于 `/overlay/napcat-lab/forward-cache/pending`。不要手动删除队列或待发送图片。

## 原生聊天数据清理调研

2026-11-11 只读占用检查：账号 `nt_db` 目录约 15.31 MiB，全局 `nt_db` 约 0.11 MiB；全局与账号表情资源合计约 170.25 MiB。当前主要占用来自表情资源，不能把整个 QQ 用户目录大小当成聊天数据库大小。检查的 22 个 `.db` 文件均没有标准 SQLite 文件头；这不单独证明具体加密算法，但不能直接用普通 SQLite SQL 清理。

NapCat v4.18.42 的内部消息服务类型中存在 `deleteMsg(peer, msgIds)`、`clearMsgRecords(peer)` 声明，存储清理服务存在 `getChatCacheInfo`、`clearChatCacheInfo` 等声明。若要定时清理，优先研究通过已登录 QQ 的内部服务执行本地清理，保留登录状态；部分参数和返回值仍是 `unknown`，仅有声明不能证明当前 QQ 二进制的具体行为、是否仅影响本地、是否释放磁盘，也不能直接开启自动任务。

公开 OneBot 的 `delete_msg` 在当前实现中调用 `recallMsg`，用于撤回消息，不应作为本地历史清理方法。

内部接口路径未启用。后续采用停止写入、备份轮换、QQ自行重建的文件维护方式，已实测恢复在线并启用容量触发定时维护；可能需要手机授权，不保留固定天数的原生历史。旧文件验证通过24小时后才删除，详见 [原生消息库定时清理](原生消息库定时清理.md)。

源码依据：[内部消息服务声明](https://github.com/NapNeko/NapCatQQ/blob/v4.18.42/packages/napcat-core/services/NodeIKernelMsgService.ts)、[存储清理服务声明](https://github.com/NapNeko/NapCatQQ/blob/v4.18.42/packages/napcat-core/services/NodeIKernelStorageCleanService.ts)、[OneBot 删除接口实为撤回](https://github.com/NapNeko/NapCatQQ/blob/v4.18.42/packages/napcat-onebot/action/msg/DeleteMsg.ts)。
